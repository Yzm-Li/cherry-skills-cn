# longtext-index · 长文本切分与省 token

一个给 **Cherry Studio 手机端** 用的 Skill：面对几十万字的项目文本，不把全文反复塞进上下文，而是**先建索引，再按需切块加载**。

目标不是“切得碎”，是“读得少，还不漏”。

## 包里有什么

```
longtext-index/
├── SKILL.md                      # 核心：盘点、切分、索引、按需加载、合并
├── README.md                     # 本文件
├── references/
│   ├── chunking-rules.md         # 边界信号、伪代码、特殊文本、质量检查
│   ├── index-schema.md           # manifest / chunks / state / 上下文头
│   ├── token-budget.md           # 估算、预算、成本模型、缓存、指标
│   └── workflows.md              # 小说、报告、会议、合同、代码库流程
```

`SKILL.md` 可独立使用；`references/` 是加餐。

## 它怎么省 token

1. **三层索引**：项目清单 → 章节目录 → 块摘要；默认只读前两层。
2. **按需加载**：先按实体/关键词/标题筛块，只读 2–5 块，必要时加前后邻居。
3. **摘要代替原文**：连续性靠“上一块摘要 + 状态卡”，不用大段重叠。
4. **状态账本**：中断可续，不从头再读。
5. **增量处理**：块哈希没变就不重做，适合反复修改的项目。
6. **成本可见**：每次报告“加载 X 块 / 共 Y 块，约占全文 Z%”。

## 切分原则

- 边界优先级：结构（卷/章/节/场景）→ 语义（视角/时间/地点/话题）→ 段落 → 句子。
- 目标大小：小说 1,200–2,000 字；论述 800–1,500 字；代码一个函数/类；合同一条。
- 不切：一句话中间、对话往返中间、代码块、表格、条款引用。
- 没有标题时，用“边界分”在目标字数附近找切点，不硬按字数切。

## 怎么装（Cherry Studio 手机端）

> 建议 0.4.0+；技能库从 0.2.1 开始提供。需要标准模式，模型支持工具调用。

### 方式 A：让 Cherry 自己创建（不用 GitHub）

1. 把 `SKILL.md` 发到手机。
2. 侧栏 **Skills（技能）** → 右上 **More（更多）** → **Create Skill（创建技能）**。
3. 把 `SKILL.md` 作为文本附件发过去，或粘贴正文。
4. 说：

   > 逐字读取附件里的 SKILL.md 正文，用 create_skill 创建一个名为 `longtext-index` 的技能，description 用文件里的原文，正文不要改写，并绑定到我当前的 Agent。

5. 批准工具调用。
6. 到 **Agent 菜单 → 编辑 → 技能** 启用。

注意：只装 `SKILL.md`，`references/` 不会带上；核心流程都在主文件里。

### 方式 B：GitHub 安装（完整包，可更新）

1. 新建 public 仓库，上传整个 `longtext-index/` 文件夹。
2. 复制文件夹链接，例如 `https://github.com/<你>/<repo>/tree/main/longtext-index`。
3. App → **Skills → Discover（发现）** 粘贴链接；或在对话里说“安装这个技能：<链接>”并批准。
4. 到 Agent 编辑里启用。
5. 更新：技能详情 → **Update skill**。

### 方式 C：不安装

把 `SKILL.md` 去掉 frontmatter 的正文，粘进 Agent 的“指令 / 提示词”。零门槛，但占上下文、不能复用。

## 怎么用

把长文本作为附件发给 Agent，然后说：

- “用 longtext-index 给这本小说建索引，先别读全文，告诉我怎么切。”
- “这本书 18 万字，主角第几章知道师父的真实身份？只读相关块。”
- “把这份 200 页报告压成一页，保留数字和页码，标出证据块。”
- “检查这 30 章的人设一致性，只读冲突候选块。”
- “这份会议记录 4 小时，按议题切，输出决议/负责人/截止时间。”
- “这份合同只看义务、例外和违约，引用条款号。”
- “代码库文档太大，先建模块索引，再回答这个接口怎么用。”

调参：

| 你说 | 它会怎么调 |
| --- | --- |
| 先建索引 | 只做 L0–L2，不读原文 |
| 只读相关 | 按问题筛 2–5 块，加邻居 |
| 省 token | 减块、用摘要、缩输出 |
| 要完整 | 分批处理全部块，报覆盖率 |
| 只要定位 | 返回块 ID/章节，不写长文 |
| 项目改了 | 按哈希只重做变化的块 |

## 适合 / 不适合

适合：

- 长篇小说、系列设定、几十万字手稿
- 报告、论文、政策文件、合同
- 会议记录、访谈、聊天导出
- 代码库文档、API 手册
- 需要反复问同一份长文本的场景

不适合：

- 几千字的短文（直接读更快）
- 只需要一次摘要、以后不再问的文本（建索引不划算）
- 图片/扫描件（先 OCR）
- 没有文件工具、也不方便在对话里维护索引的场景（仍可用，但会麻烦）

## 局限

- Token 估算是保守近似，不是精确计费。
- 切分边界靠规则和语义判断，复杂排版可能需要人工复核。
- 免费/小上下文模型仍可能装不下“索引 + 多块”，要减块。
- 它省的是上下文，不省第一次建索引的阅读成本。
- 摘要会丢细节；关键结论要回到原文块核对。
