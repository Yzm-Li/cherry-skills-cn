# 长文本智能切分与低 token 处理

## 适用

用户给了一份很长的项目文本（小说、报告、论文、会议记录、合同、代码库文档），要求摘要、问答、改写、检查一致性、翻译，或者直接说“太长了，省点 token”。

核心不是“把文本切小”，是**先建索引，再只读需要的那几块**。切分只是手段，少读才是目的。

## 三条底线

1. **不丢内容。** 每个块有唯一 ID，最终能核对覆盖率：100% 的块要么处理过，要么明确标记“跳过及原因”。
2. **不切断语义。** 不在一句话中间、一段对话中间、一个代码块中间切；标题跟着正文走。
3. **不重复付费。** 摘要、索引、处理结果都落盘；用哈希判断变更，只重做改过的块。

## 先判断，再动手

| 文本量 | 策略 |
| --- | --- |
| 8,000 字以内 | 直接读，不必建索引 |
| 8,000–30,000 字 | 先列章节/小节，按节读 |
| 30,000 字以上 | 建完整索引，按需加载 |
| 多文件项目 | 先建文件清单，再逐文件建块 |

同时确认四件事：

- 任务类型：问答、摘要、改写、一致性检查、翻译、代码审查？
- 输出预算：答案多长？要不要引用？
- 上下文窗口：模型能吃多少？留多少给输出？
- 工具：有没有文件读写、代码执行、检索工具？

没有文件工具时，就在对话里维护 Markdown 索引表；有工具时，落成 `manifest.json`、`chunks.jsonl`、`state.json`。

## 一、盘点

先看清楚，再切：

- 总字数、行数、文件数、编码。
- 结构：卷、章、节、标题、场景分隔符、代码围栏、表格。
- 语言：中文为主、英文为主、混合。
- 重复：同一文件多个版本、复制粘贴的段落。
- 版本：文件哈希或修改时间。

盘点的产出是一张**项目清单**：

```text
项目：XX
文件：12 个，共 186,400 字
结构：3 卷 / 28 章 / 无小节
语言：中文
重复：第 4 章与第 7 章有 1,200 字重复
版本：2026-10-24
```

多文件项目不要把内容拼成一个大字符串。先按文件切，再建一张全局实体表（人物、术语、产品），把同一实体的块跨文件互链。

## 二、切分

### 边界优先级

从高到低找切点：

1. **结构边界**：卷、章、节、标题、场景分隔符（`***`、`——`、空行）、代码块、表格、条款。
2. **语义边界**：视角切换、时间跳转（“三天后”“回到城里”）、地点切换、话题切换、人物组合变化。
3. **段落边界**：段首缩进、空行。
4. **句子边界**：句号、问号、叹号、分号。

永远不要在一句话中间切；不要把标题和它的第一段分开；不要把代码块、表格、引用块切开。

### 目标大小

| 类型 | 每块目标 | 说明 |
| --- | --- | --- |
| 小说/叙事 | 1,200–2,000 汉字 | 一章太长就按场景切 |
| 论述/报告 | 800–1,500 汉字 | 一节一块，长节按小节 |
| 会议记录 | 一个议题或 10–20 轮 | 决议、负责人、截止时间不拆散 |
| 合同/条款 | 一条或一组相关条款 | 定义、义务、例外放一起 |
| 代码/文档 | 一个函数/类/模块 | 保留 import、签名、注释 |
| 聊天记录 | 一个话题窗口 | 不切断一问一答 |

- 最小 300 字；太小的块合并到相邻块。
- 最大 3,000 字；超过就继续切。
- 默认不重叠；需要连续性时，只带上一块最后 1–2 句（100–200 字），或者更好：带“上一块摘要 + 故事状态”，而不是原文。

### 没有标题时怎么找边界

给相邻段落打一个“边界分”：

```text
+3  显式标题/章节标记
+2  场景分隔符
+2  时间/地点跳转
+2  视角人物变化
+1  空行/段首缩进
+1  人物或关键词重合度骤降
-2  正在对话中间
```

在目标字数附近，选分数最高的位置切。没有明显边界，就退到段落边界；再没有，退到句子边界。

有 embedding 时，算相邻段落的语义相似度，相似度骤降处加分；没有就靠上面的显式信号。

### 切完做三件事

1. **合并**：小于 300 字的块并入相邻块，除非它是独立标题/表格。
2. **编号**：稳定 ID，例如 `ch03-c002`；文件多时用 `file-slug#c012`。
3. **哈希**：每块算内容哈希，用于变更检测和缓存。

## 三、建索引

不要一上来就读原文。索引分三层：

### L0：项目清单

文件、总字数、结构、版本、哈希。

### L1：目录层

卷/章/节，每项一行摘要（不超过 40 字）+ 字数 + 块范围。

### L2：块索引

每块一条记录：

| 字段 | 内容 |
| --- | --- |
| `id` | `ch03-c002` |
| `title` | 块标题或首句缩写 |
| `path` | 卷/章/节 |
| `range` | 字符起止或行号 |
| `chars` | 字数 |
| `tokens_est` | 估算 token |
| `hash` | 内容哈希 |
| `summary` | 1–3 句，不超过 120 字 |
| `entities` | 人物、机构、产品、地点 |
| `keywords` | 3–8 个检索词 |
| `pov` | 视角人物（叙事） |
| `time` | 故事时间/文档时间 |
| `links` | 前后块、相关块 |
| `status` | pending / done / skipped |

### L3：原文块

只有需要时才读。读的时候加一个**上下文头**：

```text
[项目] XX | [章节] 第 3 章 | [块] ch03-c002 | [人物] 林晚、周野 | [前情] 上一块：两人三年后重逢
```

这样不必把上一块原文全塞进去。

### 索引形态

- 机器用：`chunks.jsonl`，一行一块。
- 人看用：`index.md`，一张表。
- 进度用：`state.json`，记录已完成块、已花 token、待办块。

## 四、按需加载

### 检索四步

1. **解析问题**：提取实体、关键词、时间、地点、任务类型。
2. **筛 L2**：先按实体/关键词过滤，再按标题和摘要打分。
3. **取块**：取分数最高的 2–5 块；需要连续性时加前后各一块。
4. **停**：预算用完，或证据已经足够回答，就停。不要“再多读一点更安心”。

### 打分

```text
score = 3×实体命中 + 2×关键词命中 + 2×标题/摘要相关 + 1×邻近问题块 - 1×已读过
```

同分时，优先选更靠近问题时间线/章节的块。

有向量检索时，用块摘要做 embedding，先向量召回，再用关键词和实体重排；没有就按上面的规则打分。摘要比原文短，建向量也更省。

### 全局问题

“这本书讲了什么”“整体有哪些风险”这类问题，不要逐块读原文：

- 先读 L1 目录摘要；
- 再读每章 L2 摘要；
- 只对差距最大的 2–3 章下钻到 L3；
- 用层级摘要合并，不重读全文。

## 五、处理与合并

### Map

每块只产出结构化笔记，不写长文：

```text
[块 ch03-c002]
事实：……
引用：“……”(第 3 段)
变化：……
疑点：……
```

### Reduce

- 按主题合并，不按块顺序堆。
- 去重：同一事实只留最可靠/最完整的一条。
- 冲突：并列，标来源块，不平均。
- 层级：块 → 章 → 卷 → 全局；每层都有字数上限。

### 状态账本

每处理一块，更新：

```text
done: ch01-c001 … ch03-c004
doing: ch03-c005
pending: ch03-c006 … ch28-c010
tokens_spent_est: 18,400
```

中断后从 `doing` 继续，不从头再来。

### 增量

文件变了，只重算哈希变化的块；索引、摘要、处理结果都按块缓存。改名不算内容变化，移动位置要更新 `path`，但块 ID 尽量不变。

## 六、Token 预算

### 估算

没有 tokenizer 时，用保守公式：

```text
tokens_est ≈ 中文字符数 × 0.8 + 英文单词数 × 1.3 + 标点/数字 × 0.5
再乘 1.2 安全系数
```

有 tokenizer 就用真实值；不要用“字数 ÷ 2”这种过度乐观的估算。

### 分配

设上下文窗口为 `W`：

- 输出预留：40% `W`
- 全局简报/故事状态：10%
- 索引切片：15%
- 原文块：25%
- 缓冲：10%

装不下就减块，不要减输出预留。长答案分两次给，比一次截断好。

### 降 token 的六个动作

1. **索引先行**：先读摘要，不读全文。
2. **摘要代替原文**：连续性靠“上一块摘要 + 状态”，不靠原文重叠。
3. **只取邻居**：需要上下文时，只加前后各一块，不全章加载。
4. **增量处理**：哈希没变就不重做。
5. **状态卡**：人物、设定、术语、决议做成一张卡，反复复用，不重复从原文抽。
6. **输出限额**：每块笔记限 150 字，最终答案按用户要求限长。

### 算一笔账

一本 120,000 字的小说：

- 直接读全文：约 120,000 字上下文。
- 建索引：60 块 × 80 字摘要 ≈ 4,800 字 + 目录 1,000 字 ≈ 5,800 字。
- 问一个问题：索引 1,000 字 + 3 块原文 6,000 字 + 状态 800 字 + 答案 1,000 字 ≈ 8,800 字。
- 单次约为全文的 7%；索引建一次，后面每个问题都省。

首轮建索引有成本，问题越多越划算；只问一次的长文本，可以直接按章节读，不必建全套索引。

## 七、不同项目的切法

| 项目 | 切分单位 | 索引用什么 | 特别注意 |
| --- | --- | --- | --- |
| 长篇小说 | 卷/章/场景 | 人物、时间线、伏笔、视角 | 不切断对话往返；维护人物状态卡 |
| 报告/论文 | 章/节/小节 | 论点、证据、数据、页码 | 数字带口径；图表标题跟正文 |
| 会议记录 | 议题/决议 | 决议、负责人、截止时间 | 不把决议和它的讨论拆开 |
| 合同 | 条款/定义 | 义务、权利、例外、期限 | 定义条款和引用条款要互链 |
| 代码库文档 | 文件/类/函数 | 模块、接口、依赖 | 保留 import、签名、代码围栏 |
| 聊天记录 | 话题窗口 | 参与者、决定、待办 | 不切断一问一答 |

## 八、输出规范

默认输出三部分：

1. **索引摘要**：项目多大、怎么切、用了哪些块。
2. **答案**：按主题组织，引用块 ID，例如 `[ch03-c002]`。
3. **覆盖率与节省**：处理了多少块、跳过多少块、加载字数占全文比例。

不要贴全文；不要列出所有块的摘要；不要把“我读了哪些块”写成流水账。

用户要“处理全文”时，分批进行，每批报告进度和剩余块；不要假装一次读完。

## 九、自检

1. 覆盖率 100% 吗？跳过的块有原因吗？
2. 有没有在一句话、一段对话、一个代码块中间切？
3. 每块有稳定 ID 和哈希吗？
4. 索引足够回答问题，而不必读全文吗？
5. 需要连续性时，加了邻居块或状态卡吗？
6. 有没有重复处理同一个块？
7. 预算守住了吗？输出预留够吗？
8. 答案里的引用能回到具体块吗？
9. 文件变更后，只重做了变化的块吗？
10. 实际加载字数占全文多少？真的省了吗？

## 十、最小示例

用户给一本 18 万字小说，问：“主角在第几章知道师父的真实身份？”

不要这样做：把全书塞进上下文，或从第 1 章开始逐章读。

应该这样做：

1. 建 90 块索引，每块 2,000 字，摘要里带人物和关键事件。
2. 解析问题：实体“主角”“师父”“真实身份”，任务“定位章节”。
3. 筛 L2：命中“师父”“身份”“揭秘”的块 7 个，按分数取前 3 个，加前后各 1 个邻居。
4. 只读这 5 块，确认第 27 章第 3 块首次揭示，第 28 章第 1 块有反应。
5. 回答：“第 27 章，ch27-c003；第 28 章 ch28-c001 有后续反应。”并报告：加载 5 块 / 90 块，约 1.1 万字 / 18 万字。
