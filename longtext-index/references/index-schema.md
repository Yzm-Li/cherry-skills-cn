# 索引结构

## 一、文件布局

```text
project/
├── manifest.json      # 项目清单
├── chunks.jsonl       # 每块一行
├── state.json         # 处理进度
├── index.md           # 人看的索引表
└── summaries/
    ├── ch01.md        # 章级摘要
    └── global.md      # 全局摘要
```

没有文件工具时，在对话里维护同样字段的 Markdown 表即可，但 ID 和哈希仍要稳定。

## 二、manifest.json

```json
{
  "project": "长夜将尽",
  "version": "2026-10-24",
  "total_chars": 186400,
  "total_chunks": 96,
  "language": "zh",
  "structure": {"volumes": 3, "chapters": 28},
  "files": [
    {"path": "book.md", "chars": 186400, "hash": "sha256:ab12..."}
  ],
  "created_at": "2026-10-24T15:00:00+08:00"
}
```

## 三、chunks.jsonl

一行一块，不要写成一个大 JSON 数组；便于流式读写和增量更新。

```json
{"id":"ch03-c002","file":"book.md","path":["卷一","第三章"],"title":"便利店重逢","start":18420,"end":20210,"chars":1790,"tokens_est":1500,"hash":"sha256:9f3c...","summary":"林晚在便利店遇见周野，两人三年后首次对话，周野回避过去。","entities":["林晚","周野"],"keywords":["重逢","便利店","回避"],"pov":"林晚","time":"2026-10-24 夜","links":{"prev":"ch03-c001","next":"ch03-c003"},"status":"pending"}
```

字段说明：

- `id`：稳定、可读、唯一；建议 `章-块`，如 `ch03-c002`。
- `path`：从大到小的结构路径，便于人看。
- `start`/`end`：原文字符偏移或行号，二选一，全项目统一。
- `chars`：块字数（不含上下文头）。
- `tokens_est`：估算 token，保留估算方法版本。
- `hash`：块原文的哈希，用于变更检测。
- `summary`：1–3 句，不超过 120 字；写“发生了什么”，不写评价。
- `entities`：人物、机构、产品、地点。
- `keywords`：3–8 个检索词，优先用原文词。
- `pov`：叙事视角人物；非叙事可空。
- `time`：故事时间或文档时间。
- `links`：前后块、相关块、引用块。
- `status`：pending / done / skipped。

## 四、state.json

```json
{
  "done": ["ch01-c001", "ch01-c002"],
  "doing": "ch01-c003",
  "pending": ["ch01-c004", "ch01-c005"],
  "skipped": [{"id": "ch28-c009", "reason": "致谢，与问题无关"}],
  "tokens_spent_est": 18400,
  "updated_at": "2026-10-24T15:20:00+08:00"
}
```

中断后从 `doing` 继续；不要从头重跑。

## 五、index.md

人看的表，不要太大：

| ID | 章节 | 标题 | 字数 | 摘要 | 人物 |
| --- | --- | --- | --- | --- | --- |
| ch03-c001 | 第三章 | 雨夜 | 1,650 | 林晚接到电话 | 林晚 |
| ch03-c002 | 第三章 | 便利店重逢 | 1,790 | 遇见周野，回避过去 | 林晚、周野 |

只列 L2；不要把每块全文贴进索引。

## 六、ID 规则

- 稳定：内容小改不换 ID；只有切分边界变化才新增/合并。
- 可读：`ch03-c002` 比 `uuid-...` 好排查。
- 唯一：多文件时加文件前缀，如 `bookA#c012`。
- 不重复使用：删除的块保留墓碑记录，避免旧引用指向新内容。

## 七、哈希与增量

- 对块原文做哈希，不要对摘要做哈希。
- 统一换行和编码后再哈希，避免 CRLF/LF 造成假变更。
- 文件级哈希用于快速判断“整文件没变”；块级哈希用于定位改动。
- 摘要、处理笔记、答案都按块 ID + 哈希缓存；哈希变了才重做。
- 移动块位置只更新 `path`/`start`/`end`，不换 ID。

## 八、上下文头

每次把块送给模型时，加一行头，替代上一块原文：

```text
[项目] 长夜将尽 | [章节] 卷一/第三章 | [块] ch03-c002 | [人物] 林晚、周野 | [时间] 2026-10-24 夜 | [前情] 两人三年后首次重逢，周野回避过去
```

头不超过 80 字，不要复制整段摘要。

## 九、索引质量检查

- [ ] 每个文件都有 manifest 记录。
- [ ] 块 ID 唯一，`links` 指向存在的块。
- [ ] 摘要能区分相邻块，不是“继续上一段”。
- [ ] `entities`/`keywords` 用原文词，便于检索。
- [ ] `tokens_est` 有统一估算口径。
- [ ] 状态文件能恢复到中断点。
- [ ] 索引总字数不超过全文的 10%。
